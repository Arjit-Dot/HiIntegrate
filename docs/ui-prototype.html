Integrations

One row per connected tool. Health comes from the latest finished scheduled or manual run. Run calls a lookup on demand.

IntegrationCategoryAuthFillsActionsScheduleLast runRecordsHealthEnabled

pull runs on a schedule and fetches many records. lookup runs on demand and returns one record. One integration can have both.

Add integration

Fill in the form. The config on the right is built live, and nothing is saved until it validates.

What the platform requires (fields marked *)
  • An integration name (a short slug), a base URL, and an authentication method with a secret name and its value (a token or password, entered once, never shown again).
  • At least one action: a mode (pull or lookup), a target schema, a method and a path.
  • A mapping for id. The platform adds source and fetched_at itself.

Templates
Starting points for each record type. Pick one and the form is filled in for you.

  

  

    
useridentity
Generic user source
Lists users, with a lookup by ID. Maps id, name, email, status and last login.
Actions: list_users (pull), get_user (lookup)

    
deviceother
Generic device source
Lists devices, with a lookup by ID. Maps id, hostname, ip, os, owner and last seen.
Actions: list_devices (pull), get_device (lookup)

    
alertalerting
Generic alert source
Lists alerts from the last 24 hours, with a lookup by ID. Normalizes severity.
Actions: list_alerts (pull), get_alert (lookup)

  

  
Each template asks for a service domain and one secret, which comes from its requires block.

Secrets
Keys and passwords are kept by name. A value can be set or replaced, and never shown again. Each one is pinned to the host it may be sent to.

  

  

    
NameStatusPinned hostUpdatedSet or replace value

  

  
Configs refer to a secret by its name only. Values are stored encrypted and are hidden in logs and responses. The platform refuses to send a secret to any host other than the one it is pinned to.
