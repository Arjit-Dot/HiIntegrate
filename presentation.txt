PRESENTATION GUIDE AND DEMO BOOK
================================================================================

How to read this book
---------------------
This book is for the person who presents HiIntegrate to the judges. It is written
like a textbook: each CHAPTER can stand alone, so it can be turned into a PDF
chapter by chapter. Commands are indented by four spaces. Anything inside
<angle brackets> is a value you replace.

Every scene in the demo follows the same pattern:
    GOAL      what the judges should believe at the end of the scene
    DO        what you click or type
    SAY       the plain-language talking points
    DATABASE  where to look in Docker to prove the change was really saved
    IF IT FAILS  the fallback

The rule of the whole demo: after every change in the browser, open the
database and show the row. Do not ask the judges to trust the screen.

Facts in this book were checked against the repository (branch main, contracts
up to contract-v6). The AI parts were rewritten on 1 Nov after the Finaltester
run on real services: Chapter 9A is the AI chapter, and every other chapter has
an "AI HERE" note and a "HOW TO PRESENT" note where they apply.
Where something is NOT built, the book says so plainly.
Judges respect honest limits more than hidden ones.

CHAPTER 1. WHAT WE BUILT, IN FIVE MINUTES
================================================================================

1.1 The one-sentence pitch
--------------------------
Adding a security tool (GitHub, Jira, Okta, anything with a REST API) means
writing a config, not code. One generic engine reads the config, calls the
service, maps the answer into common schemas, and stores it.

1.2 The problem
---------------
Every security tool has its own API: its own login style, its own paging, its own
field names, its own failure behaviour. Writing a new connector for each one is
slow and repeats the same hard parts (retries, rate limits, secrets, bad data).
We solve the hard parts once, in the engine, and describe each service in a
small file.

1.3 What the platform does, step by step
----------------------------------------
    1. A person describes a service in a config (by hand, from a template, or
       drafted by AI from the service's documentation).
    2. The platform validates the config and can test it with one real call.
    3. The engine calls the service on a schedule (a "pull") or on demand (a
       "lookup"). It handles login, paging, retries and rate limits.
    4. Every record is mapped into one of three common shapes: user, device,
       alert.
    5. Good records are stored. Bad records are quarantined, with the reason and
       the original, instead of being lost or crashing the run.
    6. A health view shows which connections are healthy, degraded or failing,
       and an email goes out when a connection keeps failing.

1.4 The three common schemas
----------------------------
    user    id, name, email, status, last_login
    device  id, hostname, ip, os, owner, last_seen
    alert   id, type, severity, timestamp, description

The platform adds two fields to every record: source (which connection it came
from) and fetched_at (when it was pulled). The original record is kept in a
column called raw.

1.5 The requirements, and where each one is shown
-------------------------------------------------
    FR-1   Authentication: API key plus another style
           bearer (GitHub), basic (Jira), API key with a prefix (Okta)
    FR-2   Endpoints, method, query parameters        any config
    FR-3   Pagination, at least two styles
           four styles are built: next link, offset, page number, cursor
    FR-4   Schedule                                   a pull "every 10s"
    FR-5   Mapping: nested values, dates              Okta's nested reply,
                                                      last_login, alert timestamp
    FR-6   Secrets safe                               Chapters 7 and 10
    FR-7   Retries with backoff                       the "flaky" mock endpoint
    FR-8   Rate limits and Retry-After                the "rate-limited" endpoint
    FR-9   Bad data is quarantined                    the "dirty users" dataset
    FR-10  Health view                                the Integrations page
    FR-11  One store, common schema                   users, devices, alerts tables

1.6 The five bonus points
-------------------------
    B-1  Incremental sync (only ask for what is new)
    B-2  Config validation with clear errors
    B-3  Test connection (one real call, nothing saved)
    B-4  Email alert on repeated failure
    B-5  Add a source through a web form
Chapter 5 shows how to demonstrate each of them.

1.7 What is on top of the brief
-------------------------------
    - AI help, always optional: draft a config from a service name or a docs
      link, suggest the field mapping from a sample, summarize the data, and fix
      quarantined records with a config change the platform proves first.
      The platform tests every AI draft itself: a real call, a second-page check
      of the paging, and rules that catch mistakes a request cannot see.
    - Several actions per integration, added at once (Add page, and "+ Actions"
      on the Integrations page), from the AI or from pasted YAML.
    - Dark mode (the moon button in the top bar).
    - People who appear in several services show up as one row.
    - Sign-in: every person has their own integrations, records, secrets.
    - An audit log, rate limits, data retention, key rotation, TLS option.

1.7a AI HERE: where the AI is used, in one line each
-------------------------------------------------
    Add integration  draft a config from a name, link, text or file   (F1-F7)
    Field mapping    suggest where each field comes from              (F8)
    Results          summarize the stored records                     (F9)
    Quarantine       propose a config change that rescues records     (F10)
    Terminal/API     explain why a run failed                         (F11)
    The map of all twelve parts, and how each is built: Chapter 9A.
HOW TO PRESENT THE OPENING: show this list, then the rule "the model proposes,
the platform proves, a person approves", before any AI scene.

1.8 The architecture in one picture
-----------------------------------
    Browser
       |
       v
    [ dashboard: nginx + React ]  -- only port published, on 127.0.0.1:5173
       |  forwards /api
       v
    [ API: FastAPI ] ---------------+
       |                            |
       |                      [ worker: scheduler ]  runs the scheduled pulls
       v                            |                and sends alert emails
    [ PostgreSQL ] <----------------+
                                    |
                           the engine calls the outside services
                           (GitHub, Jira, Okta, ... or the local mock)

    [ mock-api ] a fake service we control, used to simulate failures.

    The AI sits OUTSIDE this picture: only the API's /ai routes call it (Gemini
    over the internet), never the engine, the worker or storage.

CHAPTER 2. DESIGN CHOICES AND WHY
================================================================================

2.1 Config-driven, one engine
-----------------------------
CHOICE   There is no code per service. The engine only reads configs.
WHY      Service-specific code is where integrations rot. A config is data: it
         can be validated, versioned, edited in a form, and drafted by AI.
RESULT   Adding a service is a config row in the database, not a deployment.

2.2 Contract first
------------------
CHOICE   Before building, we wrote three contract files and a reference check:
         integration.schema.json (what a config may contain), result.schema.json
         (what stored records look like), openapi.yaml (every API route).
WHY      Two people built the backend and the frontend at the same time. The
         contract is what they both agreed to.
PROOF    "cd schema/tools && npm run check" prints "All contract checks passed".
         Fourteen deliberately broken configs in samples/invalid must each be
         rejected with exactly the expected errors. The Python validator and the
         JavaScript reference check must give the same answers. Changes to the
         contract are tagged (contract-v1 ... contract-v6) and logged in
         docs/decisions.md.

2.3 The engine is deterministic; AI stays at the edges
------------------------------------------------------
CHOICE   The path that fetches and stores data never calls an AI model. AI is
         used to advise (draft a config, suggest a mapping, propose a fix), and a
         person approves every change.
WHY      Data pipelines must be repeatable and explainable. A model can be wrong,
         so the platform checks every suggestion itself before showing it.
RESULT   With the AI key removed, the AI routes answer "501 switched off" and
         everything else works. We demonstrate this.

2.4 Strict module boundaries
----------------------------
    config_loader   reads and validates configs. No network.
    engine          makes the HTTP calls and maps records. No database.
    runner          the one place an action runs: engine, then storage, health,
                    alert. The scheduler and the API both call it.
    storage         the only code that touches the database.
    api             a thin HTTP layer. No business logic.
    ai              called only from the AI routes, so it can be switched off.

2.5 Configs live in the database (D-15)
---------------------------------------
CHOICE   One row per integration. Editing updates the row in place and raises a
         revision number. Template files are only starting points.
WHY      A config that exists both as a file and as a row drifts apart. One
         source of truth.
RESULT   "Add an action to an existing service" is an edit, and the service keeps
         its name, records and history.

2.6 Store the original, normalize a copy
----------------------------------------
CHOICE   Every record is stored twice in one row: the normalized fields and the
         untouched original (raw).
WHY      The original makes quarantine fixable without calling the service again,
         and lets us prove what the service really sent.

2.7 Quarantine instead of failing
---------------------------------
CHOICE   A bad record never stops a run. It is saved in the quarantine table with
         the reason (missing_required_field, transform_failed, invalid_value),
         the field, the original record and the run it came from.
WHY      One bad record out of ten thousand should not lose the other 9,999, and
         should not be silently dropped either.

2.8 Reliability built into the engine
-------------------------------------
    Retries      timeouts, connection errors and 5xx are retried, waiting 1, 2
                 then 4 seconds (the last wait repeats).
    No retry     wrong key (401) and other 4xx fail at once, clearly.
    429          waits for the Retry-After the service sends; if it sends none,
                 uses the normal backoff; if it asks for more than 60 seconds the
                 run fails with a clear message instead of freezing.
    Pacing       an optional minimum time between requests.
    Paging       next link, offset, page number, cursor. A page limit stops
                 runaway loops. An empty page ends a next-link walk.
    One at a time  the database refuses a second running run of the same action.

2.9 Health is judged per action
-------------------------------
CHOICE   A connection's health comes from the latest finished run of EACH action:
         failing, degraded (some records quarantined, or a field vanished), or
         healthy.
WHY      Found on real Okta: one failing action was hidden by a later success of
         another. Now a failing action cannot hide.

2.10 Schema drift check
-----------------------
If a field the config maps used to appear in the service's answer and is now
missing from every record, the run still succeeds, but the connection turns
degraded and the message names the vanished path. A field that was never there
does not raise an alarm.

2.11 People across services
---------------------------
The same person in Jira and Okta appears as one row listing both services. They
are matched by lowercased email. Users with no email are never merged.

2.12 AI design rules
--------------------
    - The model proposes; the platform proves; a person approves.
    - The model never writes to the database or a config by itself.
    - Secrets, auth headers and request headers are never sent to the model.
      Names and emails in sample records are masked before they leave.
    - A proposed fix may only change one action's mapping-related fields. It can
      never touch the login, the base URL, or secrets.
    - The AI is optional: no key means "501", and the product still works.

2.12a What the platform checks on every AI draft (new)
------------------------------------------------------
    - The draft is validated by the same validator as the form, and corrected
      by the model up to twice.
    - If the secret already exists and is pinned to the host the draft calls, the
      draft is tried on the real service (first page, nothing saved), and its
      paging is checked with a second page.
    - Rules with no model: a variable left as its example, paging whose
      parameter names cannot work, a draft reusing another service's secret.
    - Up to three correction rounds from the test's evidence. The best-testing
      draft is kept, so a bad "fix" is dropped.
    - The service's own error message is shown, and given to the model.
    - What the model is told it may NOT change: variables only the person knows.
HOW TO PRESENT: one sentence. "We do not trust the model; we test its output
the way we would test a colleague's, and we show the test results."

2.13 Technology
---------------
    API          Python, FastAPI (stateless)
    Scheduler    APScheduler, in its own worker process
    Database     PostgreSQL (SQLite for quick local runs and tests)
    Secrets      Fernet encryption (library: cryptography)
    Frontend     React, Vite, TypeScript, Tailwind, a code editor (Monaco)
    Packaging    Docker Compose: postgres, backend, worker, frontend, mock-api
    AI           Google Gemini over its REST API (model set by LLM_MODEL), with a
                 fallback model (LLM_FALLBACK_MODEL) when the main one is busy.
                 Instructions are plain text files in app/ai/prompts.

CHAPTER 3. BEFORE THE JUDGES ARRIVE: SETUP AND PRE-FLIGHT
================================================================================

3.1 What you need
-----------------
    - Docker Desktop running.
    - A .env file in the repository root (never committed). Names only here:
        POSTGRES_PASSWORD   required
        ENCRYPTION_KEY      required for stored secrets
        LLM_API_KEY, LLM_MODEL     for the AI scenes (Google AI Studio key)
        SMTP_HOST, SMTP_PORT, SMTP_USERNAME, SMTP_FROM, SECRET_SMTP_PASSWORD
                            for the email alert scene
    - Optional: DASHBOARD_PASSWORD (puts a password in front of everything).
    - Port 5173 free on your machine. If a development server uses it, stop it.

3.2 Start from a clean slate
----------------------------
A clean database avoids surprises (an old database from before the sign-in
feature is refused at startup with a clear message).

    docker compose down -v        (this deletes stored data on purpose)
    docker compose up --build -d
    docker compose ps

You should see five services: postgres, backend, worker, frontend, mock-api.
Only the frontend shows a published port: 127.0.0.1:5173.

3.3 Window layout (set this up before starting)
-----------------------------------------------
    Window 1  Browser with the dashboard at http://localhost:5173
    Window 2  Terminal "DB" with the helper functions below (database proof)
    Window 3  Terminal "LOGS" running:  docker compose logs -f worker backend
    Window 4  This book, open at the current scene

3.4 Shell helpers (paste into Window 2 once)
--------------------------------------------
    export API=http://localhost:5173/api/v1

    # run SQL inside the database container
    db() { docker compose exec -T postgres psql -U postgres -d hiintegrate "$@"; }

    # create the demo account and keep the session token
    register() {
      TOKEN=$(curl -s -X POST $API/auth/register -H 'Content-Type: application/json' \
        -d '{"username":"judge","password":"demo-password-123"}' \
        | python3 -c 'import sys,json;print(json.load(sys.stdin).get("token",""))')
      echo "token starts with: ${TOKEN:0:8}..."
    }
    login() {
      TOKEN=$(curl -s -X POST $API/auth/login -H 'Content-Type: application/json' \
        -d '{"username":"judge","password":"demo-password-123"}' \
        | python3 -c 'import sys,json;print(json.load(sys.stdin).get("token",""))')
      echo "token starts with: ${TOKEN:0:8}..."
    }

    # call the API as the demo account
    api() { curl -s -H "X-Session-Token: $TOKEN" -H 'Content-Type: application/json' "$@"; }

    # start one action now:  run_action <integration> <action>
    # (the dashboard's Run button only exists for integrations that have a lookup;
    #  a pull is started with this, or by waiting for its schedule)
    run_action() { api -X POST "$API/integrations/$1/actions/$2/run" -d '{}'; echo; }

If you set DASHBOARD_PASSWORD, add  -u admin:<that password>  to every curl.
The session token goes in the header X-Session-Token (not Authorization).

3.5 Live counters panel (optional but impressive)
-------------------------------------------------
In a spare terminal, show the size of every table, refreshing every 2 seconds.
Judges see numbers move as you click.

    while true; do clear; date; db -c "
      SELECT 'integrations' AS tbl, count(*) FROM integrations
      UNION ALL SELECT 'users', count(*) FROM users
      UNION ALL SELECT 'devices', count(*) FROM devices
      UNION ALL SELECT 'alerts', count(*) FROM alerts
      UNION ALL SELECT 'quarantine', count(*) FROM quarantine
      UNION ALL SELECT 'runs', count(*) FROM runs
      UNION ALL SELECT 'secrets', count(*) FROM secrets
      UNION ALL SELECT 'audit', count(*) FROM audit;"; sleep 2; done

3.6 Prepare the demo account and the mock secret
------------------------------------------------
The mock service needs a token. It is a public TEST value, safe to show.

    register
    api -X PUT $API/secrets/mock_token \
        -d '{"value":"mock-secret-123","host":"mock-api"}'
    (prints nothing; HTTP 204 means saved)

Then in the browser: open http://localhost:5173, choose "Create an account" or
"Sign in" with username judge and password demo-password-123.

3.7 Real services (do this BEFORE the judges, off camera)
---------------------------------------------------------
For the real-data scenes (GitHub, Jira, Okta) save their tokens under the same
demo account, with the host each token belongs to. Never show a real token.

    GitHub  secret github_token   host api.github.com
    Jira    secret jira_token     host <yoursite>.atlassian.net
    Okta    secret okta_token     host <your-org>.okta.com

Save each from the Add form's Authentication box, or from the shell with a hidden
prompt so the value never lands in your history:

    put_secret() { read -rs -p "value for $1: " V; echo
      api -o /dev/null -w "%{http_code}\n" -X PUT "$API/secrets/$1" \
          -d "{\"value\":\"$V\",\"host\":\"$2\"}"; unset V; }
    put_secret github_token api.github.com

Create the three integrations from the Templates page ("Use this template"), set
their variables (organization, site, domain), and run each once so there is real
data in the tables before the demo starts.

3.7a Prepare the AI scenes (off camera)
---------------------------------------
    1. LLM_API_KEY works (AI mode does not say "switched off").
    2. Secrets saved BEFORE the judges arrive, each pinned to its host, so the AI
       draft is tried on the real service by itself:
           okta_token     <your-org>.okta.com
           jira_token     <yoursite>.atlassian.net
           github_token   api.github.com
           nvd_api_key    services.nvd.nist.gov
       Use a separate secret name per service. (A draft that reuses another
       service's secret now gets its own name, but do not rely on it.)
    3. Know the variables to type: the Okta domain, the Jira site and email, a
       GitHub organization you can see.
    4. The NVD documentation files are in the repository: docs/api-docs/nvd/.
    5. Run every AI feature ONCE successfully, so the page has a saved draft, a
       saved summary and a saved proposal to fall back on (Appendix F).
    6. Expect each draft to take 25 to 60 seconds. Rehearse what you say while
       waiting (Chapter 9A.3).
    7. Write down numbers from your own rehearsal (rows pulled, rows
       quarantined): live data changes, and the book's numbers are examples.

3.8 Pre-flight checklist (tick everything)
------------------------------------------
    [ ] docker compose ps shows five services, backend "healthy"
    [ ] http://localhost:5173 loads and you can sign in as judge
    [ ] db -c "SELECT 1"   works
    [ ] The mock secret exists:  api $API/secrets   lists mock_token
    [ ] Real integrations have data (Results page shows users and alerts)
    [ ] The AI key works: AI mode in "Add integration" does not say "switched off"
    [ ] The AI secrets are saved and pinned (Chapter 3.7a), one rehearsal done
    [ ] Email: SMTP settings present (Chapter 5, bonus B-4 will send one email)
    [ ] No real secret value visible on any open screen or in terminal history
    [ ] Browser zoom is large enough for the back of the room
    [ ] A backup plan is ready (Appendix F)

CHAPTER 4. THE DEMO WALKTHROUGH (THE MAIN SCRIPT)
================================================================================

Total time about 30 minutes. A 10-minute short version is at the end of this
chapter. Between scenes, glance at the live counters.

--------------------------------------------------------------------------------
SCENE 0. Opening and the running system (2 minutes)
--------------------------------------------------------------------------------
GOAL     Judges see a real, running, containerised system, not slides.

DO       In the DB terminal:
             docker compose ps

SAY      "Five containers: a database, the API, a worker that runs scheduled
         pulls, the dashboard, and a mock service we use to simulate failures.
         Only the dashboard is reachable from the network, and only from this
         machine."

HOW TO PRESENT   Keep this scene short and visual. If the room is dim, press the
         moon button (top bar) for dark mode: it follows your choice next time.
AI HERE  None yet. Say in one sentence that the AI is a separate, optional layer
         and that you will show it after the core works without it.

SHOW     The PORTS column: only 127.0.0.1:5173->80 on the frontend.

--------------------------------------------------------------------------------
SCENE 1. Accounts: every person has their own data (3 minutes)
--------------------------------------------------------------------------------
GOAL     Sign-in exists, and passwords are never stored in readable form.

DO       1. In the browser, sign out, then "Create an account" as: demo2 /
            demo-password-123, and sign out again. Sign back in as judge.
         2. Show the accounts table.

DATABASE
             db -c "SELECT username, left(password_hash, 40) AS password_hash,
                           created_at FROM accounts;"
             db -c "SELECT left(token_hash, 16) AS token_hash, account,
                           expires_at FROM auth_sessions;"

AI HERE  The AI is per account too: another account's AI draft cannot use your
         keys or see your records, and the AI never receives a password or token
         (Chapter 9A.10). Show it later in Scene 10c.

SAY      "Passwords are stored only as a salted scrypt hash. A sign-in token is
         stored only as its SHA-256 hash, so a copy of the database cannot be
         used to sign in. Everything else in the database belongs to one account,
         so two people can have an integration or a secret with the same name and
         never see each other's."

IF IT FAILS  "Username taken" means the account exists: use Sign in.
HOW TO PRESENT   Sign out and in once, then go straight to the table. Do not
         dwell on screens: the proof is the database row.

--------------------------------------------------------------------------------
SCENE 2. Secrets: saved encrypted, never shown again (3 minutes)
--------------------------------------------------------------------------------
GOAL     Show that a token is encrypted in the database and cannot be read back.

DO       1. Browser: Secrets page. It lists secret names, whether each is set, the
            host it is pinned to, and when it was stored. No values.
         2. Save a throw-away secret from the shell (this is a fake value):
                api -X PUT $API/secrets/demo_token \
                    -d '{"value":"demo-value-12345","host":"mock-api"}'
         3. Show it in the database:

DATABASE
             db -c "SELECT account, name, host, left(ciphertext, 36) AS ciphertext,
                           updated_at FROM secrets ORDER BY updated_at DESC;"
         The ciphertext starts with gAAAAA... (that is a Fernet token). The
         value demo-value-12345 appears nowhere.
         4. Show the API cannot return it:
                api $API/secrets
         5. Show the logs do not contain it:
                docker compose logs 2>&1 | grep -c "demo-value-12345"
            It prints 0.

SAY      "Secrets are write-only. You can set or replace one, never read it back.
         Each one is pinned to a host and the platform refuses to send it
         anywhere else. A config only ever holds the secret's NAME."

AI HERE  The AI cannot see this: secret values are never sent to the model, and
         an AI draft only ever uses a secret that already exists AND is pinned to
         the host the config calls. Show 9A.10 if asked.
HOW TO PRESENT   Do steps 2 to 5 quickly; the "prints 0" line is the moment.

OPTIONAL PROOF (authorized decryption, using the server's own key)
             docker compose exec backend python -c "
             from app.storage import get_engine, session_scope
             from app.secrets.store import get_secret
             with session_scope(get_engine()) as s:
                 x = get_secret('demo_token', s, 'judge')
                 print(x.name, x.host, x.value)"
         It prints demo-value-12345. Say: "Only the application, holding the
         encryption key, can decrypt it. The database alone cannot."
         Do NOT run this for a real token.

--------------------------------------------------------------------------------
SCENE 3. Add a source through the form, catch a mistake, test, save
(5 minutes)   [bonus points B-5, B-2, B-3]
--------------------------------------------------------------------------------
GOAL     A person can connect a service without writing code, with clear errors
         and a safe test before anything is saved.

DO       1. Browser: "Add integration", mode Manual.
         2. Fill the form for the mock service:
              Name              demo-users
              Base URL          http://mock-api:8001
              Authentication    type api_key, placement header,
                                header name Authorization, prefix "SSWS ",
                                secret name mock_token (already saved in 3.6;
                                leave the value box empty)
              Action name       list_users, mode pull, target schema user
              Method / Path     GET   /pages/cursor
              Query parameters  limit=10
              Records path      items
              Schedule          every 1 minute (this is the FR-4 proof: the
                                worker will run it by itself)
              Pagination        cursor: parameter "after", next cursor path
                                "meta.next"
              Mapping           id: id (transform string) ... name: name,
                                email: email (lowercase), status: status,
                                last_login: last_login (datetime)
         3. DELIBERATE MISTAKE (B-2): change the Base URL to
                http://example.com
            Watch the form: the field turns red and the message says
            "must use https:// (http:// is allowed only for localhost,
            127.0.0.1 and mock-api)". The Validation tab and the editor margin
            show the same, with the line. Put the URL back.
         4. Press "Test connection" (B-3). The panel shows the status code, the
            raw first record next to the mapped record, the pages fetched ("only
            the first page") and any mapped paths that found nothing. Nothing is
            saved by a test.
         5. Press Save.

DATABASE (run right after Save)
             db -c "SELECT account, name, revision, enabled, created_at,
                           config->>'base_url' AS base_url
                    FROM integrations;"
             db -c "SELECT at, event, target, revision FROM audit
                    ORDER BY id DESC LIMIT 5;"
         The integration row exists with revision 1. The audit table shows who
         changed what: integration.created, and action.tested for the test.
         The audit log never contains secrets, config bodies or records.

SAY      "The server is the only validator, so the form, the editor, the command
         line and the API all give the same answers. A test makes one real call,
         first page only, and saves nothing. Saving writes one row; editing later
         raises the revision, not a new copy."

AI HERE  Everything in this scene can also be drafted by the AI in one button
         (Scene 10). Say so, then do it by hand first: the judges see what the
         AI is automating, and that the same validator, test and save are used
         either way. In Scene 10, point back to this one: "same checks".
HOW TO PRESENT   The deliberate mistake (step 3) and the Test panel (step 4) are
         the two moments. Slow down on them.

SHOW AN EDIT (D-15)
         Edit the integration, change the Records path wrongly, save, then:
             db -c "SELECT name, revision, updated_at FROM integrations;"
         revision is now 2: updated in place.

--------------------------------------------------------------------------------
SCENE 4. Run a paginated pull and watch the tables fill (3 minutes)
--------------------------------------------------------------------------------
GOAL     Real paging, real storage, real retrieval.

DO       1. Start the pull now:
                run_action demo-users list_users

6.1 How to open the database
----------------------------
    docker compose exec postgres psql -U postgres -d hiintegrate

Useful once inside psql:
    \dt                 list the tables
    \d integrations     describe one table
    \x                  toggle expanded output for wide rows
    \q                  quit

6.2 The tables
--------------
    accounts          username, password_hash (salted scrypt), created_at
    auth_sessions     token_hash (SHA-256), account, created_at, expires_at
    integrations      account, name, config (JSON), revision, enabled,
                      created_at, updated_at
    secrets           account, name, ciphertext (encrypted), host, updated_at
    users             account, source, id, name, email, status, last_login,
                      fetched_at, raw
    devices           account, source, id, hostname, ip, os, owner, last_seen,
                      fetched_at, raw
    alerts            account, source, id, type, severity, timestamp,
                      description, fetched_at, raw
    quarantine        pk, account, source, action, target_schema, run_id, raw,
                      reason, field, created_at
    runs              pk, account, integration, action, mode, trigger, status,
                      started_at, finished_at, duration_ms, pages_fetched,
                      records_pulled, records_valid, records_invalid, retries,
                      error
    action_state      account, integration, action, last_success_at
                      (powers incremental sync)
    path_baseline     account, integration, action, paths
                      (powers the schema drift check)
    alert_attempt     account, integration, action, at, outcome, failures,
                      message (what came of each alert email)
    audit             id, account, at, event, target, revision, request_id

Every table except accounts has the account column, and it is part of the primary
key. That is how one person's data stays invisible to another.

6.3 "Where does it happen?" map
-------------------------------
Use this when a judge asks "where is that saved?".

    You do this                         Look here
    ---------------------------------   -------------------------------------
    Create an account                   accounts, auth_sessions
    Save a token                        secrets (ciphertext, host)
    Save or edit a config               integrations (config, revision), audit
    Press Test                          runs (trigger = test), audit
    A scheduled or manual pull          runs, then users / devices / alerts
    A bad record                        quarantine (reason, field, raw)
    Incremental sync                    action_state (last_success_at)
    A field vanishes from the service   runs.error (code schema_drift),
                                        path_baseline
    Alert email                         alert_attempt
    Apply an AI fix                     integrations (revision +1), audit
    Delete old data                     runs, quarantine, audit (retention)

6.4 Query bank
--------------
Configs
    SELECT name, revision, enabled, updated_at,
           jsonb_object_keys(config::jsonb->'actions') AS action
    FROM integrations;
    SELECT config FROM integrations WHERE name='demo-dirty';     (use \x first)

Encrypted secrets (never a value)
    SELECT account, name, host, left(ciphertext, 36) AS ciphertext, updated_at
    FROM secrets;

Stored records, with the original beside the normalized copy
    SELECT id, email, raw->>'email' AS original_email,
           last_login, raw->>'last_login' AS original_login
    FROM users LIMIT 5;

Counts per source and per schema
    SELECT source, count(*) FROM users GROUP BY source;
    SELECT source, severity, count(*) FROM alerts GROUP BY source, severity;

Quarantine
    SELECT source, action, reason, field, run_id, raw FROM quarantine
    ORDER BY pk DESC LIMIT 10;
    SELECT reason, count(*) FROM quarantine GROUP BY reason;

Runs
    SELECT pk, integration, action, trigger, status, pages_fetched,
           records_pulled, records_valid, records_invalid, retries,
           error->>'code' AS error_code
    FROM runs ORDER BY pk DESC LIMIT 10;

Same person in two services
    SELECT lower(email) AS person, array_agg(source ORDER BY source) AS services
    FROM users WHERE email IS NOT NULL
    GROUP BY lower(email) HAVING count(DISTINCT source) > 1;

State and alerts
    SELECT * FROM action_state;
    SELECT * FROM alert_attempt;
    SELECT at, event, target, revision FROM audit ORDER BY id DESC LIMIT 10;

6.5 The database survives restarts
----------------------------------
Data lives in the Docker volume named hiintegrate-db. Show it:
    docker compose restart backend worker
    db -c "SELECT count(*) FROM users;"        (same number as before)
"docker compose down" keeps the data. "docker compose down -v" deletes it.


================================================================================
CHAPTER 7. ENCRYPTION AND SECRETS: HOW KEYS AND TOKENS ARE PROTECTED
================================================================================

7.1 The rule
------------
A config never holds a secret. It holds a NAME, for example
    secret: github_token
The value lives somewhere private, and the platform refuses to put it anywhere
except on a request to the host it belongs to.

7.2 Where a secret value can live
---------------------------------
    1. The encrypted store in the database (the normal way). Saved from the
       dashboard (Add form's Authentication box) or PUT /secrets/{name}.
    2. The environment, as SECRET_<NAME> in .env (the old way). These belong to
       the server as a whole, so only the one account named in
       ENV_SECRETS_ACCOUNT can use them (empty means nobody). This keeps the demo
       working without letting anyone who registers use the server's real tokens.
    3. A file, as <NAME>_FILE=/path (for ENCRYPTION_KEY, LLM_API_KEY,
       DATABASE_URL, POSTGRES_PASSWORD, DASHBOARD_PASSWORD, SECRET_<NAME>), so
       the value never appears in the container's environment listing.

7.3 How stored secrets are encrypted
------------------------------------
    - Algorithm: Fernet (from the cryptography library): AES-128 in CBC mode with
      an HMAC-SHA256 integrity check. A tampered value fails to decrypt.
    - Key: ENCRYPTION_KEY from the environment. It is never stored in the
      database and never copied into an image.
    - Rotation: ENCRYPTION_KEY accepts several keys separated by commas. The first
      encrypts new values and all of them decrypt. The command
          python -m app.cli rotate-keys
      re-encrypts every stored secret with the first key (and changes nothing if
      any secret cannot be opened).
    - Passwords: salted scrypt hash only.
    - Session tokens: only the SHA-256 of the token is stored.

7.4 Write-only
--------------
You can set or replace a secret and you can list names. You can never read a
value back through the API or the dashboard. The Secrets page shows "set" or
"not set", the pinned host and the time.

7.5 Host pinning (the strongest protection against AI-written configs)
----------------------------------------------------------------------
Each stored secret has a host. Before EVERY request, including redirects and
next-page links, the engine checks the request goes to that host. If a config
(pasted, shared, or written by AI) points a secret at another host, the run
fails with secret_host_mismatch and NOTHING is sent.

LIVE PROOF
    1. Save a config whose base_url is https://example.com and whose auth uses
       the secret mock_token (pinned to mock-api).
    2. Test or run it. The error says: "refused: secret mock_token is pinned to
       mock-api, but this request goes to example.com. Nothing was sent."

7.6 Logs never hold secrets
---------------------------
Logs are structured JSON, with a request id, and any secret value is redacted.
An audit of all container logs, every API reply, a database dump, the tracked
files and the full Git history, searched for every real secret on the machine,
found none. Show the quick version:
    docker compose logs 2>&1 | grep -c "<a fake secret value you saved>"    -> 0

7.7 What the AI can and cannot see
----------------------------------
    NEVER sent to the model: secret values, auth headers, request headers.
    Sent, but masked: sample records (the part of an email before the @ becomes
    ***, name fields become ***). At most 20 records.
    Also never sent: a password, a session token, another account's data. The
    summary gets counts (computed by the database) and at most 25 masked records.
    The AI's real test never returns record contents to the browser: it reports
    which paths were found. A draft may only use a secret that already exists and
    is pinned to the host the config calls; if it reuses a secret pinned to
    another service's host, it is given its own secret name.
    Honest note: masked samples and documentation text leave the machine and go
    to Google's Gemini service. If that is not acceptable, leave LLM_API_KEY
    unset: the AI routes answer 501 and nothing else changes.

HOW TO PRESENT CHAPTER 7: Scene 2 is the show; use this chapter for questions.
AI HERE: 7.7 above, and Scene 11 step 8. The strongest AI sentence is "the model
never holds a key": it only ever sees the NAME of a secret.

7.8 What an attacker with access would get
------------------------------------------
    - A copy of the database alone: encrypted secrets they cannot decrypt, hashed
      passwords, hashed session tokens. Configs and records are readable.
    - The database and ENCRYPTION_KEY: they can decrypt secrets. Protect the key
      (use a *_FILE secret, restrict the host).
    - Someone with Docker access can still read environment variables of a
      running container. File-based secrets narrow this; they do not remove it.


================================================================================
CHAPTER 8. THE OUTPUT SCHEMA: SAVED AND RETRIEVED
================================================================================

8.1 What "output schema" means here
-----------------------------------
The common shapes that every service is converted into. They are defined in
schema/result.schema.json, and the engine checks every mapped record against
them before saving.

    user    id, name, email, status, last_login
            status is one of: active, inactive, suspended, unknown
    device  id, hostname, ip, os, owner, last_seen
    alert   id, type, severity, timestamp, description
            severity is one of: low, medium, high, critical, unknown

Dates are normalized to UTC ISO format (for example 2026-01-01T09:00:00Z), whether
the service sent ISO text, a different text format, or epoch seconds or
milliseconds. Every record also carries source, fetched_at and raw.

8.2 How mapping gets there
--------------------------
The config says, for each field, where to find it (a path into the record) and
what to do with it:
    path        where the value is (nested paths like profile.email work, and
                "a || b" means use the first that exists)
    transform   string, int, float, bool, lowercase, uppercase, datetime
    value_map   translate fixed values, for example ENABLED -> active
    default     use this when the value is missing
    required    fields that must be present, or the record is quarantined

8.3 Saved
---------
Show it (Scene 4):
    SELECT id, email, raw->>'email' AS original_email, last_login,
           raw->>'last_login' AS original_login FROM users LIMIT 3;
The same row holds the normalized value and the original.

8.4 Retrieved
-------------
Through the API (all need the session token):
    api "$API/results?target=user&limit=5"             stored users
    api "$API/results?target=alert&source=demo-incremental"
    api "$API/results?target=device"
    api "$API/users/unified?limit=5"                   one row per person
    api "$API/quarantine?limit=5"                      rejected records
    api "$API/quarantine/export" > quarantine.json     all of them, one file
    api "$API/runs?integration=demo-users&limit=5"     run history
    api "$API/integrations/demo-users"                 config + health + alert
Through the dashboard: Results page (Table or JSON view, People or Records for
users), Quarantine page (filters and "Export all"), Run history.

HOW TO PRESENT CHAPTER 8: open one users row with the raw column
(Scene 4's last query), then one quarantine row. Two queries, two screenshots.
AI HERE: the summary and the Fix with AI both read these tables: the summary reads
counts and a masked sample, the fix reads the raw originals. Say that the raw
column is what makes the AI fix provable without calling the service again.

8.5 One person, many services
-----------------------------

================================================================================
CHAPTER 9. QUARANTINE AND THE AI FIX
================================================================================

9.1 Why records get quarantined
-------------------------------
    missing_required_field   a required field (always id) is missing or empty
    transform_failed         the value cannot be converted (a date that does not
                             exist, text where a number was expected)
    invalid_value            the value is outside the allowed set (a status that
                             is not in the value_map and has no default), or it
                             breaks the output schema

Each quarantine row holds: which integration and action, the schema, the run, the
reason, the field, the time, and the ORIGINAL record. Per config, on_invalid can
be "quarantine" (the default) or "skip" (drop and count).

9.2 The demo dataset
--------------------
The mock service's /dirty/users sends five users:
    u-1, u-2       good
    (no id)        missing_required_field on id
    u-bad-date     transform_failed on last_login (the date 31/31/2025)
    u-banned       invalid_value on status (the status "banned")
With the demo-dirty config (Appendix C-2) the first run saves 2 users and
quarantines 3.

9.3 How the AI fix works (and why it is safe)
---------------------------------------------
    1. The platform collects the quarantined originals for that action and
       groups them by reason and field.
    2. The model sees the action's config (without request headers), the groups
       and up to 20 masked originals, and replies with SMALL CHANGES by path, for
       example: set actions.dirty_users.map.status.value_map to a map that also
       contains banned -> suspended.
    3. The platform applies those changes itself, to a copy of the stored
       config, and only inside this action's map, required, on_invalid,
       records_path, request.query, request.path and pagination. A change to the
       login, the base URL or secrets is ignored.
    4. The result is validated. If invalid, the model is asked once more with the
       errors. If still invalid, it cannot be applied.
    5. The platform maps the stored originals again with the new config (a dry
       run, nothing saved) and reports "rescues N of M", with up to three mapped
       samples.
    6. A person presses Apply. Apply is the normal save (PUT /integrations/{id}).
       It is refused if the integration was edited after the proposal was made.

9.4 What to expect in the demo
------------------------------
    Proposal:    add "banned" to the status value map (usually banned -> suspended
                 or inactive)
    Verification: Rescues 1 of 3. Still quarantined: 2 (missing id, impossible
                 date). Say so: "The other two are genuinely bad data. The fix is
                 partial, and the platform tells us exactly how partial."
    After Apply and a new run:
        - the users table gains u-banned
        - the new run reports 2 quarantined (the two bad ones, again)
        - the old quarantine rows are NOT deleted: quarantine is an append-only
          record of what each run rejected, so the total goes UP by 2 even though
          the problem is fixed. Look at the latest run's counts, not the total.
          (Old rows are removed by the retention job, 90 days by default.)

9.5 If the proposal is not what you expected
--------------------------------------------
The model's wording varies. The count is what matters, because the platform
computes it. If the proposal proposes something odd, show that it can be
rejected: close the window without applying; nothing changed (revision stays the
same). If the AI is unavailable, the page shows the last saved proposal, marked as
saved, and it can only be applied if the integration has not changed.

9.5a AI HERE and HOW TO PRESENT CHAPTER 9
----------------------------------------
    AI here      Fix with AI (F10) and the run explanation (F11); Chapter 9A.8.
                 New: Apply is disabled when a proposal rescues nothing, and the
                 model also sees the service's own error text.
    How to       Scene 7, then 9A.8's NVD numbers (98 valid and 2 quarantined,
    present      then 100 and 0). Always say "rescues N of M": the count is the

9A.3 F1 to F7: "Add integration" in AI mode, what really happens
----------------------------------------------------------------
Type a service name, press Generate draft. Behind the one button:

    1  FIND DOCS   The model suggests documentation URLs. The platform fetches
                   each one safely (https only, public addresses only, every
                   redirect checked, size and time limits) until a page lists
                   real endpoints. It tries up to 14 pages, follows links on
                   pages that load but are not the reference, and asks the model
                   again if every guess failed.
    2  DRAFT       The model writes a config in YAML from that page.
    3  VALIDATE    The platform validates it with the SAME validator the form
                   uses. Errors go back to the model, up to twice (F5).
    4  TIDY        Variables get example values; value-map keys become text;

                   on real Okta).
    5  OWN SECRET  If the draft reuses a secret that is pinned to ANOTHER
                   service's host, it gets its own name instead.
    6  REAL TEST   Only if a secret with that name already exists AND is pinned
                   to the host the config calls: one real call, first page, plus
                   a second page ONLY to check the paging (F6). The secret is
                   never sent anywhere the AI chose.
    7  CORRECT     If the test shows a problem the draft can fix (a path that

                   advance), the evidence goes back to the model, up to three
                   rounds. The draft that tests best is kept, so a "fix" that
                   makes things worse is discarded.

NINE FIXES MADE DURING THE RUN (say this: it shows a test-and-fix loop):
    1  Errors now carry the service's own reason.
    2  A 400, 404 or 422 refusal goes back to the model.
    3  Up to three correction rounds, keeping the best draft.
    4  A "fix" that hides a missing field behind a constant no longer wins.
    5  A secret check that wrongly renamed Okta's secret was corrected.
    6  A login the service refuses goes back to the model.
    7  A scheme written as the header name, or a prefix with no space, is tidied.
    8  An OAuth stand-in is announced.
    9  Summary counts cover every stored record, and Apply is disabled when a
       proposal rescues nothing.

9A.13 What the AI cannot do (say it before they ask)
----------------------------------------------------
    - Read a site that needs JavaScript and publishes no spec (NVD). You supply
      the document.
    - Know a value only the person knows (your org, your account id). The
      platform points it out; the model is told not to change it.
    - Log in with OAuth client credentials or sign requests (AWS): refused.
    - Express a range in a value map (AbuseIPDB score to severity).
    - Ask a service for fields it does not return by default (Jira "fields"):
      it can try, and the test shows what is still missing.
    - Be right every time. It is checked every time, and a person decides.
    - Explain a failed run on screen (API only for now).
    - Keep working with no key: the AI is optional by design.

10.3 What is NOT built (say it before they ask)
-----------------------------------------------
    - A guard in the ENGINE on where requests go (D-17 S-6): host pinning protects
      the secret, but a config could still make the server call an internal
      address. The AI documentation fetcher has this guard; the engine does not
      yet.
    - Pinning the resolved address in the AI documentation fetcher (a changing
      DNS answer between check and connect could slip through).
    - AI hardening against hostile documentation text steering the model (the
      allow-list and the host pin limit the damage; this is not complete).
    - OAuth2 service logins (reserved in the schema, refused by the validator).
      When the documentation asks for OAuth client credentials, the AI draft says
      it fell back to a plain token that will expire (found with Sophos).
    - Reading documentation that needs JavaScript and publishes no spec (NVD):
      a person supplies the document.
    - Ranges in a value map (AbuseIPDB's 0 to 100 score to low..critical).
      Okta's management API needs a private-key JWT for service apps.
    - No password reset, no roles, no sharing between accounts, no account
      deletion.
    - No database migrations: tables are created at startup. An old database is
      refused with a clear message and must be recreated.
    - Login throttle and rate limits live in one process's memory.
    - The CI workflow has not yet run on GitHub (its commands were run locally).
    - Over plain http, passwords and tokens travel unencrypted: use the TLS
      overlay for anything beyond your own machine.

CHAPTER 11. DEPLOYMENT AND SCALABILITY

11.1 What the Docker setup is
-----------------------------
One file, docker-compose.yml, defines five services:

    postgres    the database (image postgres:16), data in the volume
                hiintegrate-db, not published to the host
    backend     the API (FastAPI under uvicorn), internal port 8000
    worker      the scheduler: same image as the API, different command
                (python -m app.worker)
    frontend    nginx serving the built React app and forwarding /api to the
                backend; the only published port (127.0.0.1:5173)
    mock-api    the local test target; never a data source; gets no .env

Two Dockerfiles: backend/Dockerfile (API, worker and mock share it) and
frontend/Dockerfile (build the app, then serve it with nginx). Services start in
order using health checks: Postgres, then the API (which creates the tables),
then the worker and the dashboard. Containers restart on failure.

Variants:
    docker compose up --build -d                                 normal
    docker compose -f docker-compose.yml -f docker-compose.debug.yml up
                      also publish the API (8000) and mock (8001) on 127.0.0.1
    docker compose -f docker-compose.yml -f docker-compose.tls.yml up
                      HTTPS (needs certs/tls.crt and certs/tls.key)

AI HERE AND HOW TO PRESENT CHAPTER 11
-------------------------------------
    The AI scales differently from the rest: it is a call to an outside service
    (Gemini), so cost and speed follow the number of drafts, summaries and fixes,
    not the number of records. A draft is a handful of model calls plus up to
    three correction rounds (25 to 60 seconds). A summary is one call. The AI
    routes are rate limited per account (20 a minute), and a fallback model takes
    over when the main one is busy. The data path never calls it.
    How to present: after "How it scales", add this one slide. It answers the
    cost question before it is asked.

11.2 How it would be deployed
-----------------------------
Smallest real deployment: one virtual machine (any cloud) with Docker.
    1. Install Docker. Clone the repository.
    2. Create .env: POSTGRES_PASSWORD, ENCRYPTION_KEY, SMTP and AI settings.
       Prefer *_FILE secrets for the keys.
    3. Put certificates in certs/ and use the TLS overlay; set
       DASHBOARD_PASSWORD; set ALLOW_REGISTRATION=false after creating accounts.
    4. docker compose -f docker-compose.yml -f docker-compose.tls.yml up -d --build
    5. Back up the database volume (pg_dump) and the ENCRYPTION_KEY separately.
       Without the key, stored secrets cannot be decrypted.

Growing up from one machine:
    - Build the images once in CI and push them to a registry, then pull the same
      images everywhere (the same image runs anywhere; settings come from
      environment variables).
    - Move PostgreSQL to a managed database and point DATABASE_URL at it.
    - Run the three app services as separate deployments (for example on
      Kubernetes, ECS, or Nomad), behind a load balancer with TLS. Each service
      has its own image name and can be scaled or moved on its own.
    - Keep secrets in the platform's secret manager and mount them as files
      (the _FILE settings already support this).

11.3 How it scales, component by component
------------------------------------------
    Dashboard   Static files. Add copies behind a load balancer, or serve from a
                CDN.
    API         Stateless: sessions live in the database, not in memory. Run
                several copies behind a load balancer. (Caveat: the login
                throttle and the rate limits count per process, so with N copies
                each counts alone.)
    Worker      Scheduling is in its own process, so scaling the API never
                duplicates timers. Safety with more than one worker: the database
                refuses a second running run of the same action (a partial unique
                index), so two workers cannot start the same run twice. To grow
                throughput, the runner is the single entry point, so APScheduler
                can be replaced by a job queue (RQ or Celery) without touching
                the engine. The worker re-reads the database every 15 seconds,
                so config changes take effect without a restart.
    Engine      Per-service pacing (the minimum time between requests) is tracked
                per process; with several workers it needs shared storage such as
                Redis.
    Database    PostgreSQL: many writers, indexes, and a retention job that stops
                tables growing without limit. Records are upserted by
                (account, source, id) so repeated pulls do not duplicate. Next
                steps: read replica for the dashboard, partition by account.
    Services    Adding a service adds a row, not code or a deployment. The work
                grows with the number of configs, not with the code.
    AI          Called only on demand, with its own rate limit (20 a minute per
                account) and a fallback model when the main one is overloaded.
                The product demos fully with AI off.

11.4 What does not scale yet (honest list)
------------------------------------------
    - No job queue: API-triggered pulls run in the API process; scheduled ones in
      the worker.
    - Pacing, rate limits and login throttle are per process.
    - Tables are created at startup with no migrations.
    - One database, no high availability or multi-region setup in this repo.
    - Retention does not shorten a long failure streak counted from old runs.

11.5 The one-sentence answer
----------------------------
"Everything runs from one command with Docker; each part is a separate container
that can be scaled or moved on its own; the API is stateless; scheduled work is
isolated in a worker that is safe to duplicate; and the part that grows fastest,
adding services, needs no code at all."

CHAPTER 12. QUESTIONS AND ANSWERS
================================================================================

Keep answers short, then offer to show it.

Q1. Why configs instead of code?
A.  Code per service is where integrations rot. A config can be validated, edited
    in a form, versioned, and drafted by AI, and the hard parts (retries, rate
    limits, secrets, bad data) are written once. Show: Scene 3.

Q2. How long does it take to add a new service?
A.  Minutes: type the service name in AI mode, check the draft, enter the token,
    test, save. By hand, a template plus a few fields. Show: Scene 10 or 3.

Q3. What if a service changes its API?
A.  The schema drift check: if a field that used to appear is gone from every
    record, the connection turns degraded and the message names the path. Records
    that can no longer be mapped go to quarantine instead of disappearing.

Q4. What happens to bad data?
A.  It is quarantined with the reason, the field and the original record, and can
    be exported or fixed by changing the mapping. Show: Scene 7.

Q5. How are tokens protected?
A.  Encrypted at rest (Fernet), write-only, pinned to one host and checked on
    every request, and kept out of logs and out of the AI. Show: Scene 2 and 7.5.

Q6. What if the AI writes a config that tries to steal a token?
A.  The token is pinned to its host: a request to another host is refused before
    anything is sent. The AI's proposed fixes are limited to one action's mapping
    fields, validated, dry-run, and approved by a person. Not fully solved:
    hostile documentation text steering the model is listed as future hardening.

Q7. Does the AI change data on its own?
A.  Never. It proposes; the platform validates and measures the proposal; a
    person presses Apply or Save.

Q8. Does anything depend on the AI?
A.  No. Remove the key and the AI routes answer "switched off" while everything
    else works. Show: remove LLM_API_KEY, restart, use the app.

Q9. What data goes to the AI provider?
A.  Documentation text, masked sample records (emails before the @ and names are
    hidden, at most 20 records) and counts. Never secrets or headers. It goes to
    Google's Gemini service.

Q10. How do you avoid duplicate records?
A.  Records are saved by (account, source, id), so pulling again updates the same
     row. Incremental sync also avoids re-fetching.

Q11. What happens if the service is slow, down or rate-limiting you?
A.  Timeouts and 5xx are retried with backoff 1, 2, 4 seconds. A 429 waits for
    Retry-After (or the backoff), and gives up with a clear error if the wait is
    over 60 seconds. A wrong key fails at once without retries. Show: Scene 6.

Q12. How do you know a mapping is right?
A.  Test connection shows the raw record beside the mapped one and lists paths
    that found nothing; the AI mapping suggestion checks every path against a
    real sample; the drift check watches it afterwards.

Q13. What if two runs overlap?
A.  The database allows only one running run per integration action. A second one
    is skipped by the scheduler or answered with 409 by the API.

Q14. What if the worker is down?
A.  The data already stored is unaffected. Scheduled pulls resume when it comes
    back. The API and the dashboard keep working.

Q15. How does the email alert avoid spamming?
A.  One email when the failure streak reaches the threshold. A success resets the
    streak, so a later streak can alert again. A failed send is logged, recorded,
    and never fails a run.

Q16. Why PostgreSQL?
A.  Many concurrent writers, JSON for configs and original records, constraints
    that enforce one running run per action, and easy to move to a managed
    database. SQLite is used only for tests and quick local runs.

Q17. Why store the raw record too?
A.  Quarantine becomes fixable without calling the service again, and we can prove
    what the service really sent.

Q18. Does it support OAuth2 or webhooks?
A.  Not yet. They are reserved in the schema and the validator refuses them with a
    clear message. API key, bearer and basic logins work. Okta's management API
    would need a private-key JWT, which is the next login type to add.

Q19. Is it multi-user?
A.  Yes: accounts, with everything (integrations, records, runs, secrets, audit)
    owned by one account. Not built: roles, sharing, password reset, account
    deletion.

Q20. How do you handle personal data?
A.  Names and emails are masked before leaving for the AI, sign-in passwords are
    hashed, secrets are encrypted, and a retention job deletes old runs,
    quarantined originals and audit entries. There is no per-person delete route
    yet.

Q21. How would this scale to hundreds of services and customers?
A.  Services are rows, so they add no code. The API is stateless and can be
    replicated; the worker is isolated and safe to duplicate; the next steps are a
    job queue behind the runner, shared rate-limit state, and database
    partitioning. See Chapter 11.

Q22. How was it tested?
A.  Over 360 automated tests, a contract check with 14 deliberately broken
    configs, a failure rehearsal script run against the packaged stack, a
    secret audit of logs, replies, database, files and history, and an attack
    script against the sign-in isolation.

Q23. What is not finished?
A.  Be direct: the engine's own guard on where requests go (S-6), full AI
    hardening (S-14), OAuth2, migrations, roles and reset. Real Okta devices
    depend on a device being enrolled in the Okta org. The CI workflow has not yet
    run on GitHub. We named each of these in docs/decisions.md.

Q24. Where does the "real" data come from? Is the mock cheating?
A.  The mock only simulates failures and bad data. The real sources are GitHub
    (users), Jira (users) and Okta (users and alerts); one person on Jira and Okta
    appears once. For devices, Okta returns them only when a device is enrolled.

Q25. Why Gemini?
A.  A team choice for the hackathon; the model name is a setting, and a fallback
    model is used when the main one is overloaded. Swapping providers touches only
    the AI client.

Q26. What does "contract" mean and why tag it?
A.  The three files that both halves of the team built against. A tag marks each
    agreed version, and every change is logged in docs/decisions.md.

Q27. What happens to scheduled pulls after I edit a config?
A.  The worker re-reads the database every 15 seconds and updates its schedule.
    No restart.

Q28. Can I see who changed what?
A.  Yes. The audit log (GET /audit) lists changes with the time, the event, the
    target and the revision, per account. It never stores a value or a config
    body. Scheduled runs are in run history instead.

Q29. How would you recover from a leaked token?
A.  Revoke it at the service, replace it (PUT /secrets/{name}), and the old value
    is overwritten. Because tokens are pinned and never logged, the leak path is
    limited to the machine holding the encryption key.

Q30. If I stop Docker, do I lose data?
A.  No. The data is in the hiintegrate-db volume. Only "docker compose down -v"
    deletes it.

AI QUESTIONS (added 1 Nov)

Q31. What if the AI drafts a wrong config?
A.  It is never saved on its own. The platform validates it, tests it on the real
    service when it can, shows "Check:" lines for what is still wrong, and the
    person presses Save. On real services the AI was wrong about: sending an
    Okta token as bearer, leaving an example variable, a paging parameter that
    cannot work, and reusing another service's secret. The platform caught each
    one. Show: Scenes 10 and 10a.

Q32. How do you know the AI's draft really works?
A.  We run it. If the secret exists and is pinned to the host, the draft makes
    one real call, plus a second page to check the paging. The result (found
    paths, errors, the service's own message) goes back to the model for up to
    three corrections, and the best-testing draft is kept. Show: Scene 10.

Q33. Can the AI read any documentation site?
A.  No. Sites that draw themselves with JavaScript give an empty page. The reader
    looks for the OpenAPI file behind them, the usual addresses, a public
    repository, llms.txt and the sitemap. NVD offers none, so the AI could not
    read it, said so, and we supplied the documentation as a file. Show: Scene
    10c.

Q34. Why not use a headless browser to read those sites?
A.  It would add hundreds of megabytes to the image, need a writable cache that
    our read-only containers do not allow, and add an attack surface (a browser
    that follows any URL). Looking for the machine-readable spec first solves
    the common case; a document attached by hand solves the rest. A headless
    browser is a possible next step.

Q35. Does the AI see my data or my keys?
A.  Never a key, a password, a header or another account's data. It sees
    documentation text, and masked sample records (names and emails hidden, at
    most 20 for a fix, 25 for a summary). The summary's numbers come from the
    database. The real test of a draft keeps record contents on the server.
    Show: 7.7 and Scene 11 step 8.

Q36. How often is the AI called, and what does it cost?
A.  Only when a person presses an AI button. A draft is several model calls (find
    docs, draft, up to two validation fixes, up to three test fixes); a summary
    or a fix is one or two. AI routes are limited to 20 a minute per account, and
    a fallback model is used when the main one is busy. The data path never calls
    it.

Q37. What did you find when you tested the AI on real services?
A.  Nine problems, all fixed (Chapter 9A.11): errors without the service's
    reason, refusals not sent back to the model, only one correction round, a
    "fix" that hid a missing field behind a constant, a wrongly renamed secret,
    a refused login not sent back, an auth header written with the scheme as its
    name, an OAuth stand-in not announced, and summary counts from a sample.
    Open problems, said plainly: NVD's site needs a supplied document, Cloudflare
    was blocked by an invalid key, AbuseIPDB's score cannot map to severity with
    a value map, Jira issues need a "fields" parameter.

Q38. Why did Cloudflare fail?
A.  Not the AI. The key we were given was refused by Cloudflare ("Invalid API
    Token"), and the account id was unknown, so the draft ran with the example
    id and Cloudflare answered 404. The platform said so: "Check: Variable
    account_id is still the example value", and showed Cloudflare's own message.
    With a valid token and the real account id it is a one-step retest.

Q39. What if the model is rate limited or down?
A.  The client retries and then uses a fallback model. If both fail the page
    offers the last saved draft, summary or proposal, marked as saved. With no
    key at all every AI button says "AI is switched off" and nothing else changes.

Q40. Could the AI change a config by itself or send a secret somewhere?
A.  No to both. A fix may change only one action's map and request path, query
    and paging; auth, base URL and secrets are not on the allow-list. A secret is
    pinned to one host and refused for any other, whatever the config says. Show:
    Scene 11 step 8 and the 13.7 test in Finaltester.md.

          last_login: { path: last_login, transform: datetime }

        on_invalid: quarantine

    Expected: run 1 saves 2 users (u-1, u-2) and quarantines 3
    (missing_required_field/id, transform_failed/last_login, invalid_value/status).
    After the AI fix adds banned -> suspended: 1 of 3 rescued.
    Note: there is deliberately NO default on the status map. A default would hide
    the problem.

C-3  demo-alert (the email alert)
---------------------------------
    version: 1
    name: demo-alert
    display_name: "Demo: a connection that breaks"
    category: other

C-4  demo-incremental (incremental sync)
----------------------------------------
    version: 1
    name: demo-incremental
    display_name: "Demo: incremental sync"
    category: other
    description: "Asks only for alerts newer than the last successful run."
    enabled: true
    requires:
      secrets: [mock_token]
    base_url: "http://mock-api:8001"
    auth: { type: api_key, in: header, name: Authorization, prefix: "SSWS ", secret: mock_token }
    actions:
      list_alerts:
        mode: pull
        target_schema: alert
        schedule: every 1h
        request: { method: GET, path: /alerts, query: { since: "{{now - 24h}}" } }
        incremental: { param: since, value: "{{state.last_success_at}}" }
        records_path: items
        map:
          id: { path: id, transform: string }
          type: type
          severity: { path: severity, value_map: { info: low, warning: medium, error: high, critical: critical }, default: unknown }
          timestamp: { path: created_at, transform: datetime }
          description: message
        required: [id, timestamp]
        on_invalid: quarantine

    Expected: run 1 pulls 4 alerts (the ones from the last 24 hours), run 2 pulls
    0. Wait a second between the two runs.

APPENDIX F. If something goes wrong during the demo
---------------------------------------------------
    The AI draft is wrong
        Good: that is the story. Show the "Check:" line or the failed test, say
        what the platform found, then fix it by hand (the form is the same one).
    The AI says it cannot find the documentation
        Say "that site needs JavaScript" and attach a document (for NVD:
        docs/api-docs/nvd/README.md). Show the list of pages it tried.
    A real service answers 401 or 403
        The key or its scope is the person's. Show the service's own message in
        the test notes. For Okta check the header prefix "SSWS ", for GitHub the
        token scopes, for Cloudflare that the token is valid.
    A draft shows "Check: Variable ... is still the example value"
        Set the variable (your org, site, domain, account id) and test again.
    An AI scene fills the wrong secret
        Check the Authentication box: the secret name must be this service's own.
        The form warns in red before a value would move another service's pin.
    The AI is slow or fails
        The first call can take up to a minute. A fallback model is used if the
        main one is overloaded. If it still fails, use the saved draft, summary or
        proposal (the pages offer them), and say "this is the saved result from
        our rehearsal run".
    The email does not arrive
        Show the alert state on the Integrations page and the alert_attempt row
        (outcome sent) and the worker log line. Say delivery depends on the mail
        provider.
    A service is rate-limiting you
        That is the feature. Show the run history: the wait and the retry.
    A page shows an old state
        Reload the browser tab. The Integrations list refreshes on reload.
    "Port 5173 already in use"
        Stop the other program (a development server) and run docker compose up
        again.
    "The database was created by an older version"
        Run docker compose down -v and start again (this deletes stored data).
    You are signed out
        The session ended: sign in again (or run login in the terminal).
    Everything is broken
        Open the recorded run-through video, if you made one, and talk over it.
        Otherwise walk through Chapters 2, 7 and 10 with the code and the
        documentation (docs/decisions.md) open.

APPENDIX G. Glossary
--------------------
    Action        one thing an integration can do (list users, look up a user)
    Alert state   what came of the alert email for a failing connection
    Audit log     the record of who changed what
    Config        the description of one service: where, how to log in, what each
                  action does
    Contract      the shared files both halves of the team built against
    Dry run       re-mapping stored records with a proposed config, saving nothing
    Drift         a field the service used to send that has disappeared
    Engine        the code that calls services and maps records
    Fernet        the encryption scheme used for stored secrets
    Health        healthy, degraded, failing, never run, disabled
    Host pinning  a secret may only be sent to the host it was saved for
    Incremental   asking only for what is new since the last successful run
    Integration   a connected service (one config row)
    Lint          rules that catch mistakes a request cannot show (an example value
                  left in, paging that cannot work)
    Lookup        an on-demand action that returns one record
    Mapping       where each schema field comes from in the service's answer
    Probe         the second page the test fetches only to check the paging
    Pull          a scheduled action that returns many records
    Quarantine    the place bad records go, with the reason and the original
    Proposes/proves/approves   the AI rule: the model suggests, the platform
                  checks, a person decides
    Raw           the untouched original record, stored beside the normalized one
    Revision      a number that goes up each time a config is edited
    Runner        the single place an action is run and recorded
    Schema        the common shape of a record (user, device, alert)
    Secret        a token or password, stored encrypted and referred to by name
    Worker        the process that runs scheduled pulls and sends alert emails
